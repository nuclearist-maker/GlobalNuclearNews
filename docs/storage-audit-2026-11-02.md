## Root cause

Historical-only PNG blobs account for **1,714,738,344 bytes**, about 96% of historical-only uncompressed content. Historical `assets/` blobs total 1,761,089,381 bytes. Examples include `assets/images/theory/series-01/hybrid-v3/008-thumbnail.png` (4,340,591 bytes) and other multi-megabyte theory illustrations. Deleting originals or replacing them with WebP reduces HEAD and deployment sizes but does not remove reachable old binaries. Already compressed images generally gain little from Git compression; different encodings remain different blobs.

Current `assets/images/` total 328,674,879 bytes; all current WebP paths total 326,189,796 bytes. QA/theory is 18,466,826 bytes and QA/history is 14,059,410 bytes, including a copied release site under `qa/history/releases-20260929/site/`. Current exact duplicate path content adds only 1,828,327 bytes across 84 groups; Git already stores each identical blob once. Deduplicating these URLs offers little Git savings and creates link risk. Revision snapshots are excluded by `public_files.collect` but remain in Git for traceability.

The October 31 commit increased the current tracked tree by 19,999,512 bytes, about 19.1 MiB. That batch alone does not explain the accumulated 2 GB. Publishing uses timestamp-based image conversion; identical output is already deduplicated by Git, so touching an unchanged file is not itself a new Git blob. Different generated bytes, however, accumulate. The publisher now avoids rewriting byte-identical converted/copied outputs. Existing image dimensions, quality and URLs are preserved.

## Implemented controls

- Final Pages output: warning at **750,000,000 bytes**, failure at **900,000,000 bytes**, before artifact upload. These are project policy thresholds, with headroom below GitHub's limit. Measurements include generated sitemap, archive, RSS and advertising files. Largest ten output files are logged. Both Pages deployment and local publisher use the same build.
- Gross new unique blobs: warning at **25,000,000 bytes**, failure at **100,000,000 bytes**, compared to the previous tree or staged index. Deletions cannot offset new binary additions. New files at least 5,000,000 bytes receive individual warnings. The publisher blocks before commit/push and leaves staged work available for review.
- Storage audit runs on PRs and main pushes; weekly Monday at 12:17 UTC and manual runs include full reachable history. Routine runs use shallow checkout and fetch only the comparison base; only periodic history audits download the full history. Results appear in logs and Actions job summaries. No auto-created issues or messages.
- New QA PNG/JPEG captures and copied QA `site/` trees are ignored. Existing tracked evidence remains intact. Ignore rules do not prevent changes to already tracked evidence; review those diffs and avoid force-adding new captures.

Commands:

```sh
python tools/storage_budget.py
python tools/storage_budget.py --history  # full clone required
python tools/storage_budget.py --base <commit>
python tools/storage_budget.py --staged
python tools/build_en_site.py
```

Threshold warnings are intentionally advisory; a single historical large repository is not a deployment failure. The full audit makes the existing excess visible without blocking every future change. The new-blob check compares trees, so it is an approximate growth guard rather than exact pack growth; a blob present only in older history may be counted as new again, and intermediate blobs introduced then removed inside a multi-commit push are not counted by the endpoint comparison. Periodic full-history audit captures actual accumulation.

## Options and safe next steps

| Option | Link continuity | Existing Git size reduction | Tradeoff |
|---|---|---|---|
| Current controls, keep WebP, avoid regenerating unchanged assets | All URLs retained | None | Safest immediate control of growth |
| Store future QA/screenshots/release copies as Actions artifacts or durable external archives | Public URLs retained | None | Define retention/export policy; do not rely on expiring artifacts for permanent QA records |
| Optimize selected oversized images at the same path after visual review | URLs retained | Usually increases history initially | Smaller site; lossy compression needs review of diagram labels and detail |
| Reuse a shared URL for future repeated assets | Existing URLs retained | None | Reduces future site duplication; keep old paths as compatibility assets |
| External object storage/CDN for future images | Existing URLs retained | None | New service, cost, backups and availability; existing site remains valid |
| Move existing images to external storage | Requires path proxy/compatibility plan | None without history rewrite | GitHub Pages cannot transparently proxy old image paths; defer |
| Untrack/archive existing QA or old snapshots | Public URLs can remain | Tiny HEAD reduction only | Requires explicit review; old blobs still in history |
| Rewrite Git history or start a clean repository | Can preserve website paths | Substantial | Separate approval, backup, collaborator coordination and reference/tag/PR migration required |
| Git LFS migration | Needs separate Pages asset materialization | No reduction without history migration | Pages does not directly serve LFS pointer files; not an immediate remedy |

Do not run filter-repo, BFG, force push, mass deletion or image migration under this change. Ordinary garbage collection cannot discard reachable historical blobs. At 750 MB warning, plan image hosting/site partitioning before reaching the 900 MB project stop. Capacity is based on bytes per future post, not a guaranteed post count. If future batches resemble the last 25-post batch (~20 MB), growth remains material even with WebP.
